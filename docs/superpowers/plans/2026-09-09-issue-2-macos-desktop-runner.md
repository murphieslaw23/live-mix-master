# Issue #2 macOS Desktop Baseline Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn LiveMixMaster into a reproducibly launchable macOS desktop application baseline with a committed Flutter runner, explicit native-library loading, actionable startup failure behavior, deterministic CI evidence, and developer documentation.

**Architecture:** macOS is the first supported desktop host. The Flutter runner is generated by pinned Flutter tooling rather than hand-authored; the native C++ engine remains a separately built shared library. Dart startup resolves the native dylib through an explicit ordered locator (environment override, repo-local development build, app-bundle Frameworks), then either enters the mixer or renders an actionable blocking startup screen. GitHub Actions builds both layers, verifies the dylib is packaged into the debug app bundle, and performs a process-level launch smoke test.

**Tech Stack:** Flutter 3.47.2, Dart 3, macOS/Xcode, CMake 3.20+, C++17, `dart:ffi`, GitHub Actions.

**Spec:** GitHub Issue #2 — `https://github.com/murphieslaw23/live-mix-master/issues/2`

## Global Constraints

- Initial officially supported desktop target is macOS only; Windows and Linux remain planned and must not be implied as verified.
- Generated Xcode/Flutter runner files must come from `flutter create --platforms=macos .`; do not hand-create the generated project structure.
- Native capture/DSP correctness is outside Issue #2; do not claim real audio capture until Issue #3 supplies device-backed PCM evidence.
- Keep capture, DSP, disk I/O, network/fingerprinting, and blocking native work off the Flutter UI thread.
- No credentials or machine-specific absolute paths enter the repository.
- Missing native-library startup must fail with an actionable operator/developer message rather than a raw `DynamicLibrary.open` exception.
- CI and local commands use Flutter 3.47.2 to match the existing repository CI contract.

### Task 5: Build, package, and launch-smoke the macOS host in CI

**Files:**

- Modify if needed: `.github/workflows/ci.yml`

**Interfaces:**

- Produces: discoverable CI proof that the native dylib builds, the Flutter app builds, the dylib is copied into the app bundle, and the executable starts.

- [ ] **Step 1: Add the permanent macOS workflow**

```sh

flutter analyze --no-fatal-warnings --no-fatal-infos

cmake -S native -B build/native -DCMAKE_BUILD_TYPE=Debug

flutter build macos --debug
```

- [ ] **Step 2: Verify the native build output exists**

```sh
test -f build/native/liblive_mixer_engine.dylib
```

- [ ] **Step 3: Package the dylib into the debug app bundle**

```sh
APP="build/macos/Build/Products/Debug/live_mix_master.app"
mkdir -p "$APP/Contents/Frameworks"
cp build/native/liblive_mixer_engine.dylib "$APP/Contents/Frameworks/liblive_mixer_engine.dylib"
test -f "$APP/Contents/Frameworks/liblive_mixer_engine.dylib"
```

- [ ] **Step 4: Perform a process-level launch smoke**

```sh
EXEC="$APP/Contents/MacOS/live_mix_master"
"$EXEC" > /tmp/live-mix-master-launch.log 2>&1 &
PID=$!
sleep 5
kill -0 "$PID"
kill "$PID"
wait "$PID" || true
```

If the process exits before the probe, upload the log and keep the job red.

- [ ] **Step 5: Upload launch/build evidence**

Upload `/tmp/live-mix-master-launch.log` and the debug `.app` (or a zipped app artifact if action size permits) with the workflow run.
